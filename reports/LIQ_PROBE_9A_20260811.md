# 任务卡 9A：爆仓数据可获取性双地点对照测试

- **测试日期**：2026-08-11
- **目的**：确认各交易所实时爆仓数据在不同地点的可获取性，并判定"零数据"是**地理封锁**还是**代码/订阅问题**
- **范围**：纯测试。未接入任何生产链路、未修改 `/opt/btc-trader` 下任何现有文件、未改动数据库与 `.env`、未重启任何 supervisor 服务、测试脚本未接入 supervisor
- **测试代码位置**：`/opt/liq-probe/`（94.16.118.7）、`~/liq-probe/`（89.58.0.82）、`~/liq-probe/`（43.128.29.190）

### 1.4 对照通道设计与两处补充诊断连接

每个交易所同时订阅「爆仓流」与「高频对照流」。**对照流是本次判定的核心**：对照流有数据而爆仓流零数据 → 排除地理封锁，指向代码/订阅问题。

烟测阶段发现任务卡指定的订阅方式存在两个会污染结论的干扰因素，故补充了带标签的诊断连接：

| 干扰因素 | 现象 | 补充的诊断连接 |
|---|---|---|
| Binance 组合流连上后完全静默（0 消息 0 错误 0 响应），无法区分"整条 WS 不投递"与"组合流里某个流名不被接受" | 见第三节 | `Binance-rawCtl`（raw 单流端点 `/ws/btcusdt@aggTrade`，只订阅对照流）<br>`Binance-rawLiq`（raw 单流端点 `/ws/!forceOrder@arr`，只订阅爆仓流） |
| Bybit 把 3 个 topic 放在一次 `subscribe` 里，只要 `liquidation.BTCUSDT` 无效，**整批订阅被拒**，对照流 `publicTrade` 也拿不到数据，会把 Bybit 误判成"地理封锁" | 见第三、五节 | `Bybit-perTopic`（同一端点，3 个 topic 分别单独 subscribe，互不牵连） |

另对 Gate 增加了 `futures.public_liquidates` 附加探测（任务卡要求"若公开频道不可用则记录错误"，该探测正是为回答"公开频道到底存不存在"）。

## 五、判定结论

### 5.1 判定表

| 交易所 | 判定 | 依据 |
|---|---|---|
| **Binance** | **接入层不可用（WS 行情层对本次全部三个数据中心 IP 均不投递数据）** | 见 5.2 |
| **Bybit** | **代码/订阅问题** | 见 5.4 |
| **OKX** | **可用**（爆仓流与对照流都有数据） | 见 5.5 |
| **Gate** | **代码/订阅问题** | 见 5.6 |
| **Hyperliquid** | 连通性正常（本卡不判定清算） | 见 5.7 |

### 5.2 Binance —— 不是"无爆仓事件"，也不是流名写错

按任务卡的判定树，"两条流都零数据"应归为**地理封锁**。实测结果比这更特殊，需要精确表述：

**观测事实**：

1. 四种连接方式（组合流 / raw 单流 × 爆仓流 / 对照流）在**三个 IP、两个国家**上全部零消息。
2. 连接层**完全健康**：三节点各只连了 1 次、成功 1 次、**0 次重连、0 个异常**。脚本设置了 `ping_interval=20, ping_timeout=20`，若服务端不响应协议层 ping，websockets 会在 20 秒内抛 `ConnectionClosed` 并触发重连 —— 4 小时零重连意味着**服务端持续正常响应心跳，只是不发任何业务数据**。
3. 无任何错误响应、无未归类消息（`errors=[]`、`subscribe_acks_raw=[]`、`unmapped_messages=[]`）。
4. **同一台机器的 Binance REST 完全正常**：本报告第二节的窗口 K 线（240 根）就是三节点各自从 `https://fapi.binance.com/fapi/v1/klines` 取到的，`source="binance-fapi"`、`errors=[]`。

**排除"无爆仓事件"**：Binance 侧的对照流是 `btcusdt@aggTrade`（逐笔聚合成交）。窗口内 BTC 振幅 0.70 %、其他三家交易所合计记录了 29 万余笔成交 —— **4 小时零条 aggTrade 在物理上不可能是"没有成交"**，只能是通道不投递。对照流在此处独立完成了"排除无事件"的任务，无需外部交叉核对。

**排除"代码/订阅问题"**：raw 单流端点 `/ws/btcusdt@aggTrade` 是最简形式，无组合流封装、无订阅报文、无流名拼接，仍然零数据。故不是 `!forceOrder@arr` 流名或组合流 URL 格式的问题。

**对"地理封锁"的修正**：香港节点同样零数据，且握手仅 156.8 ms（比德国快约 5 倍，网络路径极佳）。因此这**不是德国 IP 特有的地区封锁**。三个 IP 的共同点是都属于云服务商数据中心（netcup AS197540 × 2、Tencent AS132203 × 1）。综合"WS 握手成功 + 心跳正常 + 零业务数据 + REST 正常"这一组合特征，更准确的表述是：**Binance 的 WS 行情层对本次测试涉及的数据中心 IP 静默不投递数据**。本次测试**不能区分**这是按 ASN/数据中心段的策略、还是账号/来源要求的变化 —— 要区分需要一个非数据中心的住宅或移动出口 IP 做第四个对照点，本次不具备该条件。

> **对生产的意义**：`monitor/liquidation_monitor.py` 的 `binance_listener()` 在 30 天日志中零事件，与本次结果完全吻合。该通道的失效**不是代码缺陷**，改代码无法修复。

### 5.4 Bybit —— 代码/订阅问题（结论明确）

**两条独立证据**：

1. **`liquidation.BTCUSDT` 这个 topic 已经不存在**。三节点应答完全一致：`{"success":false,"ret_msg":"error:handler not found,topic:liquidation.BTCUSDT"}`。这是服务端明确告知"没有这个处理器"，不是网络问题、不是权限问题。
2. **替代 topic `allLiquidation.BTCUSDT` 完全可用**。同一条连接、同一时刻订阅返回 `{"success":true}`，并在窗口内投递了 **34 / 34 / 33** 条 BTC 爆仓事件；对照流 `publicTrade.BTCUSDT` 投递 6.6–7.1 万条。

**附加发现 —— 故障放大机制**：Bybit 的 `subscribe` 是**整批语义**。卡片指定的方式（3 个 topic 放在一次 `subscribe` 的 `args` 里）只收到**一条**失败应答，`allLiquidation` 与 `publicTrade` 全部为 0；而逐 topic 分别订阅时三条应答分离、后两条成功。也就是说：**一个失效 topic 会连带废掉同一条连接上的所有订阅**。

> **对生产的意义**：`monitor/liquidation_monitor.py` 的 `bybit_listener()` 订阅的正是 `liquidation.BTCUSDT`（单 topic），30 天零事件由此完全解释。这是**可以通过改代码修复**的（改用 `allLiquidation.BTCUSDT`）。本卡不做修复。

### 5.5 OKX —— 可用

爆仓流与对照流均有数据，三节点一致，订阅确认正常，0 重连 0 异常。这是五家中唯一无需任何改动即可用的通道，与生产现状（OKX 是唯一有数据的通道）一致。

### 5.6 Gate —— 代码/订阅问题（结论明确）

**证据**：

1. `futures.liquidates` 是**私有频道**，服务端明确要求认证：`{"error":{"code":4,"message":"authentication required for Channel futures.liquidates"},"result":{"status":"fail"}}`（三节点一致）。任务卡要求"若公开频道不可用则记录错误"，此即该错误的原文。
2. **存在可用的公开频道 `futures.public_liquidates`**：订阅返回 `{"result":{"status":"success"}}`，窗口内投递 **32 / 32 / 32** 条 BTC_USDT 爆仓事件（三节点完全相同，前 3 条样本逐字节一致）。
3. 交叉核对（5.3 节）确认窗口内 Gate 确有爆仓（REST 40 条）。

→ 零数据的原因是**订阅了需要认证的私有频道**，而公开频道存在且工作正常。属代码/订阅问题。

> **对生产的意义**：生产的 `monitor/gate_liq_monitor.py` 走的是 REST 轮询而非 WS（其文件头注释写着"Gate.io WS futures.liquidates 需认证，REST 无需认证"—— 该判断本身是对的，但**遗漏了 `futures.public_liquidates` 这个公开 WS 频道**）。本次实测表明 Gate 爆仓数据有 WS 实时通道可用，无需 REST 轮询。另外，WS 公开频道返回的 `result` 里**同样没有 `order_id`**，这与 `LIQ_AUDIT_20260811.md` 中"生产代码强制要求 `order_id` 导致 41 天零落库"的根因完全吻合，构成第三条独立印证。

### 5.7 Hyperliquid —— 连通性正常

任务卡指定"仅测连通性与响应时间，不判定清算"。三节点各轮询 476 / 476 / 479 次，**HTTP 200 占比 100 %**，无一次失败。

> 与生产形成鲜明对照：生产 `hyperliquid_poller()` 在 30 天日志中有 **79 次轮询失败**（`Read timed out` / `ConnectionResetError(104)`）。本次 4 小时零失败，说明生产那些失败更可能与 `timeout=10`（本次用 15s）、轮询间隔或当时网络状况有关，而非端点不可用。

## 七、局限与不确定性

1. **香港节点运行时环境未对齐**：Python 3.9.5 / websockets 15.0.1 / aiohttp 3.13.5，德国为 3.10.12 / 16.1.1 / 3.14.3。原因是该机只有 Python 3.8.10 且 deadsnakes 的 `Packages` 索引无法取得。脚本 md5 三地一致。不影响判定（判定依据是订阅应答原文与对照流有无数据）。
2. **"法兰克福"实为纽伦堡**；且德国两节点同城同 ASN，德国侧内部不构成跨地点对照。
3. **窗口非严格同时**：香港后移 14 分 26 秒，重叠 3 h 45 min。三节点各跑满 14400 s，计数可比但采样时段不完全重合。
4. **OKX 计数是全币种**（`instType=SWAP`），不可与 Bybit / Gate 的 BTC 专属计数横比。BTC 专属数据见 5.3 节。
5. **Binance 的"数据中心 IP"假说未被独立验证**：本次三个 IP 全部是云服务商机房。要区分"按 ASN/机房段策略"与"其他原因"，需增加一个住宅/移动出口 IP 作为第四对照点。
6. **Coinglass 交叉核对不可用**（付费墙），`data.binance.vision` 的 `liquidationSnapshot` 路径 404。Binance 侧因此没有第三方源直接确认同窗口确有 BTCUSDT 爆仓 —— 但其对照流 `aggTrade` 4 小时零条已足以排除"无爆仓事件"（见 5.2）。
7. **窗口内 BTC 爆仓活动清淡**（OKX BTC ≥$1 万仅 3 笔）。振幅 0.70 % 虽满足卡片门槛，但爆仓样本量偏小（Bybit 34、Gate 32）。若需更大样本，应在剧烈波动时段重跑。
8. **Bybit `allLiquidation` 与 `liquidation` 的字段差异未展开测试**：本次只确认前者可用并取到样本，未验证其字段语义、是否等价于旧 topic、是否有聚合行为。改造生产前需补做。

## 八、发现的问题清单

> 仅列问题，不含修复方案（本卡禁止修复）。

**P0**

1. **Bybit 生产订阅的 topic 已被服务端下线**：`liquidation.BTCUSDT` 三地均返回 `error:handler not found`。生产 `monitor/liquidation_monitor.py:bybit_listener()` 用的正是这个 topic，30 天零事件由此完全解释。可用替代 `allLiquidation.BTCUSDT` 已实测有数据（34/34/33 条）。
2. **Bybit 整批订阅语义会放大单点故障**：一次 `subscribe` 里放多个 topic，任一无效则**整批被拒**，同连接上其他订阅全部拿不到数据（实测卡片指定方式下 3 条流全为 0，逐 topic 订阅时后两条正常）。
3. **Gate 生产判断遗漏了公开 WS 频道**：`futures.liquidates` 确需认证（已实证），但 `futures.public_liquidates` 是可用的公开频道（订阅 success，32 条数据）。`monitor/gate_liq_monitor.py` 文件头注释"WS 需认证，故用 REST"的结论因此不完整。
4. **Binance WS 行情层对本次全部三个数据中心 IP 静默不投递数据**：四种连接方式 × 三个 IP × 两个国家全部零消息，同时握手成功、心跳正常、0 重连、0 错误、REST 完全可用。该通道失效不是代码缺陷，改代码无法修复。

**P1**

5. **`gate_liquidations` 缺少 `order_id` 得到第三条独立印证**：Gate WS 公开频道的 `result` 与 REST 的记录**都没有 `order_id` 字段**（本报告 4.2、5.3 节样本）。这与 `LIQ_AUDIT_20260811.md` 中"生产代码 `if not order_id: return` 导致 41 天零落库"的根因一致，且证明该字段是 Gate 接口本就不提供、而非偶发缺失。
6. **OKX 生产订阅口径是全市场**：`instType=SWAP` 会收到全部永续合约的爆仓（本次 4 小时 1,748 条，其中 BTC ≥$1 万仅 3 笔），绝大部分消息被 `instId.startswith("BTC")` 过滤丢弃。功能正确但带宽与解析开销放大约 500 倍。
